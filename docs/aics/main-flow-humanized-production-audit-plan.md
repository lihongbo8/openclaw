# AICS 主流程拟人化生产级审计与改版方案

## 结论

当前主流程已经形成 `经营概览 → 数据分析 → 归因分析 → 公司目标 → 规划方案 → 任务调度 → 岗位执行` 的页面链路，但它还没有达到“生产级拟人化可用”。

核心问题不是页面缺少按钮，而是页面没有像一个运营助手一样持续回答：

- 我现在在哪一层？
- 这一层为什么存在？
- 当前缺什么？
- 下一步点哪里？
- 点不了时怎么修？
- 上一层证据和下一层产物是什么？

因此第一轮改版不应继续堆功能，而应统一为“主流程驾驶舱 + 每层任务卡 + 阻塞修复入口”的体验。

## 拟人化生产级测试标准

每一层页面必须通过以下检查：

1. **一句话定位**：用户 3 秒内知道这一页负责什么。
2. **证据链可见**：能看到上一层输入和本层输出。
3. **下一步明确**：页面主按钮只有一个主动作，其他动作降级为辅助。
4. **禁用可解释**：任何 disabled 按钮旁边必须显示原因和修复入口。
5. **阻塞可修复**：每个 blocker 至少映射到一个可点击页面，例如 API 管理、费用与授权、规划方案。
6. **业务语言优先**：默认不显示 `CompanyGoal`、`PlanningPackage`、`TaskPackage`、`DispatchToRoleRequest` 等后端对象名；只在详情/调试区展示。
7. **闭环可追踪**：每层都显示 `来源 → 当前处理 → 下一层产物`。
8. **空状态不空**：没有数据时必须给“为什么没有”和“去哪里创建”。
9. **生产安全边界**：页面不能绕过 AICS 层级直接执行岗位、调用 provider、生成正式执行任务。

## 页面审计

### 经营概览

现状：

- 有经营意图输入框和主流程状态。
- `发起经营意图` 在空输入时禁用。

问题：

- 状态卡偏工程统计，缺少“当前建议做什么”。
- 用户不知道应该填写什么粒度的经营意图。
- 发起后会流向数据分析，但页面缺少显式“下一站”说明。

改版：

- 增加“运营助手建议”区域：根据当前 read model 判断推荐动作。
- 输入框下提供 3 个业务模板：商城授权提升、岗位供给补齐、执行成功率提升。
- 提交成功后显示“已生成数据分析包，去数据分析确认”。

### 数据分析

现状：

- 展示观察包、事实数、观察域。
- 空状态能回经营概览。

问题：

- “观察域”虽多，但没有区分内部数据、外部数据、风险数据、可吸收能力。
- 用户看不到哪些数据是真实采集、哪些缺失、哪些过期。
- 确认观察包按钮禁用时缺少解释。

改版：

- 四组数据区：内部经营、云端商城、本地 OpenClaw、外部机会/风险。
- 每个信号显示：来源、采集时间、可信度、是否可用于归因。
- 增加“缺失数据清单”和“重新采集”入口。

### 归因分析

现状：

- 有“生成真实归因”按钮。
- 没有观察包时按钮禁用。

问题：

- 禁用时用户不知道要先去数据分析确认。
- 归因维度偏系统化，缺少“主因/次因/证据/影响”的经营表达。
- 归因生成后到目标层的承接不够明显。

改版：

- 顶部展示“归因前置条件”：观察包、证据数、可信度、确认状态。
- 归因结果按 `主因 / 影响 / 证据 / 建议目标` 展示。
- 主按钮文案根据状态切换：
  - 没观察包：`去数据分析`
  - 观察未确认：`确认观察后归因`
  - 已就绪：`生成真实归因`

### 公司目标

现状：

- 页面标题为“目标管理”，入口叫“公司目标”。
- `创建候选目标` 在缺归因时禁用。

问题：

- “公司目标”和“目标管理”命名不一致。
- 用户不知道目标来自哪条归因。
- 目标确认后到规划方案的下一步不够强。

改版：

- 统一标题为“公司目标”。
- 每个目标卡显示：来源归因、指标、周期、负责人、确认状态。
- 禁用创建目标时显示“需要先完成归因分析”并提供入口。
- 确认目标后主 CTA：`去规划方案拆解`。

### 规划方案

现状：

- 同时承担公司管理看板和主流程规划方案。
- 展示工作块、岗位承接、任务状态。

问题：

- 页面名称叫“规划方案”，内容标题叫“公司管理看板”，语义冲突。
- 用户难以区分“经营拆解”和“正式可调度规划”。
- `生成并确认规划方案` 禁用时缺少修复路径。

改版：

- 页面分两个区：
  - `经营拆解看板`：目标 → 工作块 → 岗位承接 → 任务候选。
  - `正式规划包`：确认后供任务调度读取。
- 若没有确认目标，显示“去公司目标确认目标”。
- 规划成功后显示“已生成 X 个待派发工作项，去任务调度”。

### 任务调度

现状：

- 已改为“任务调度 · 派发中心”。
- 主按钮为“检查并派发”。
- 空状态可去规划方案。

问题：

- 阻塞信息仍偏底层，例如 `cloud_capability_not_authorized`。
- “能力组合解析”对运营人员价值不够直接。
- 缺少“这次会派给哪些岗位、为什么选这些岗位”的解释。

改版：

- 增加“派发候选卡”：工作项、推荐岗位、匹配原因、预计产物、风险。
- blocker 映射为业务语言：
  - 未授权：去费用与授权。
  - API 缺失：去 API 管理。
  - 能力未授权：去能力/商城授权。
  - 规划缺失：去规划方案。
- 点击“检查并派发”前显示预检清单，成功后跳转岗位执行。

### 岗位执行

现状：

- 已改为“岗位执行 · 执行控制台”。
- 能看到派发任务、执行队列、人工确认、费用授权。

问题：

- `先完成岗位授权` 是正确提示，但没有把授权缺口解释清楚。
- 执行队列为空时缺少“回到派发中心创建任务”的强入口。
- 结果产物区在空状态下不够突出。

改版：

- 顶部增加“当前不能运行的原因卡”：缺授权、缺费用确认、缺 API、缺工具/Skill。
- 空队列提供主按钮：`返回派发中心`。
- 执行完成后展示产物、日志、失败原因、可归因信号和是否写回。

## 统一交互模型

每层页面统一为 5 个固定区：

1. **阶段头部**
   - 页面名称
   - 这一层做什么
   - 当前阶段状态
   - 主 CTA

2. **前置条件**
   - 上一层是否完成
   - 当前缺什么
   - 修复入口

3. **本层工作区**
   - 当前数据/候选/报告/任务
   - 可操作列表

4. **输出预览**
   - 本层会交给下一层什么
   - 数量、状态、可信度、风险

5. **安全边界**
   - 允许动作
   - 禁止动作
   - 为什么不能绕过下一层

## 前后端改动方案

### 前端

- 新增主流程统一组件：
  - `MainFlowStageHeader`
  - `MainFlowPreconditions`
  - `MainFlowBlockerList`
  - `MainFlowOutputPreview`
  - `MainFlowPrimaryAction`

- 六层页面改为同一交互骨架：
  - 经营概览：经营意图与推荐动作。
  - 数据分析：观察信号与数据可信度。
  - 归因分析：主因、证据、影响、建议目标。
  - 公司目标：候选目标、确认状态、规划入口。
  - 规划方案：经营拆解和正式规划包。
  - 任务调度：派发候选和预检结果。
  - 岗位执行：执行队列、阻塞、产物。

### 后端 / Read Model

- 在 `AicsMainFlowReadModel` 增加统一字段：
  - `stageGuidance`: 当前阶段说明、主动作、下一步。
  - `preconditions`: 前置条件列表。
  - `blockerResolutions`: blocker → 修复页面/动作。
  - `handoffPreview`: 下一层可读取的产物预览。

- 保持现有实体边界不变：
  - 数据分析不创建目标。
  - 归因不创建规划。
  - 规划不直接执行岗位。
  - 调度才生成正式派发单。
  - 岗位执行只消费已派发任务。

### UI 文案

- 默认使用业务词：
  - `CompanyGoal` → 公司目标
  - `PlanningPackage` → 规划方案
  - `RolePlanItem` → 岗位工作项
  - `TaskPackage` → 派发单
  - `DispatchToRoleRequest` → 执行队列项
  - `RoleResult` → 执行结果

- 后端对象名只放在详情抽屉或调试说明里。

## 测试方案

### 拟人化 E2E

新增一组“运营人员首次使用”测试：

1. 空系统进入经营概览，能看到经营意图模板。
2. 填写经营意图后，能生成数据分析包并进入数据分析。
3. 数据分析未确认时，归因按钮显示去数据分析/确认观察。
4. 归因完成后，公司目标能显示来源归因。
5. 公司目标确认后，规划方案能生成岗位工作项。
6. 规划工作项存在后，任务调度显示派发候选。
7. 缺授权/API/能力时，任务调度显示可点击修复入口。
8. 派发成功后，岗位执行出现队列。
9. 岗位执行缺授权时，引导费用与授权。
10. 执行完成后，产物和结果可见。

### UI 回归

- 所有 disabled 主按钮必须有可见原因。
- 所有空状态必须有下一步按钮。
- 页面正文不得出现裸露后端对象名，除非在详情/调试区。
- 页面不得显示隐藏 fallback 文本。

## 优先级

### P0：让链路能被普通运营人员使用

- 统一每层的阶段头部、前置条件、主 CTA。
- 禁用按钮必须显示原因和修复入口。
- 空状态必须有下一步。
- 任务调度和岗位执行保持当前边界。

### P1：让链路能被生产验证

- 增加 `stageGuidance / preconditions / blockerResolutions / handoffPreview` read model。
- 加拟人化 E2E 测试。
- 加页面对象名隐藏测试。

### P2：让链路超过普通生产级

- 每层加入“系统建议下一步”。
- 每个 blocker 给出业务解释和影响范围。
- 每个输出都显示证据、可信度、风险、下游使用方式。
